# Docusaurus Documentation Sites

Use Docusaurus for a versioned documentation portal when React, MDX, structured
navigation, internationalization, or theme customization provides enough value
to justify a Node.js build pipeline. Keep simple documentation in Markdown when
a README and a small set of guides are sufficient.

## Verify Before Implementing

Docusaurus, Node.js, React, MDX, plugins, and deployment platforms evolve
independently. Before scaffolding or upgrading:

1. Check the [current Docusaurus release and installation
   requirements](https://docusaurus.io/docs/installation).
2. Check the [migration guides](https://docusaurus.io/docs/migration) for every
   crossed major release.
3. Confirm that the selected Node.js release is supported by Docusaurus and by
   the deployment platform.
4. Verify plugin compatibility with the selected Docusaurus release.
5. Pin all `@docusaurus/*` packages to the same compatible version and commit
   the package-manager lockfile.

Do not copy a version number from this handbook. Select the latest supported
stable release compatible with the project and verify it from official
metadata.

## Site Shape

A typical site contains:

```text
docs/
src/
static/
docusaurus.config.ts
sidebars.ts
package.json
<package-manager lockfile>
```

Prefer TypeScript configuration when the project already uses TypeScript:

```typescript
import type {Config} from "@docusaurus/types";
import type * as Preset from "@docusaurus/preset-classic";

const config = {
  title: "ACME Documentation",
  url: "https://docs.acme.com",
  baseUrl: "/",
  onBrokenLinks: "throw",
  presets: [
    [
      "classic",
      {
        docs: {
          sidebarPath: "./sidebars.ts",
        },
      } satisfies Preset.Options,
    ],
  ],
  themeConfig: {
    navbar: {
      title: "ACME Documentation",
    },
  } satisfies Preset.ThemeConfig,
} satisfies Config;

export default config;
```

Keep `url`, `baseUrl`, and `trailingSlash` aligned with the real hosting path.
For a site hosted at `https://acme.com/platform/`, use
`url: "https://acme.com"` and `baseUrl: "/platform/"`. Test this path in a
production build rather than relying only on the development server.

## MDX Is Executable Content

MDX can contain JSX, imports, exports, and React components. Treat it as source
code, not as inert Markdown.

- Allow MDX only from trusted, reviewed authors and repositories.
- Never compile customer, issue, comment, ticket, retrieved, or other untrusted
  text as MDX.
- For untrusted content, parse into a constrained Markdown schema, reject raw
  HTML, JSX, imports, exports, and unsupported URLs, then render with a
  non-executable pipeline.
- Review custom remark and rehype plugins as build-time code.
- Do not expose secrets through configuration, generated pages, client
  bundles, source maps, or `customFields`.
- Treat plugin output and remote content fetched during the build as untrusted
  input. Validate schemas, content size, destinations, and failure behavior.

Build isolation is still required for trusted repositories because dependencies
and plugins execute with the build process identity. Use a least-privilege CI
identity, read-only source access where possible, bounded network egress, and no
production secrets.

## Navigation and Content Ownership

- Give every document a stable ID and one clear owner.
- Prefer autogenerated sidebars for predictable directory trees. Use explicit
  sidebars when product ordering differs materially from file layout.
- Avoid duplicating authoritative content across current and versioned docs.
- Use descriptive links and let the production build detect broken internal
  links and assets.
- Keep redirects for moved public pages and test them during migrations.
- Separate tutorial, how-to, reference, and explanation pages rather than
  combining incompatible reader goals.

## Versioning

Docusaurus versioning creates snapshots under `versioned_docs/` and
`versioned_sidebars/`. A snapshot is another maintained copy, not a free
feature.

- Version documentation only when users operate multiple supported product or
  API versions.
- Prefer snapshots for supported major or material compatibility lines, not
  every patch release.
- Keep unreleased or continuously updated content in `docs/`.
- Create snapshots through the Docusaurus versioning CLI. Do not hand-copy the
  generated directory structure.
- Patch a versioned page only when the corresponding released behavior still
  needs correction.
- Limit preview builds with `onlyIncludeVersions` when all historical versions
  make local or preview builds too slow.
- Publish migration guides separately from version snapshots.

See the official [versioning
guide](https://docusaurus.io/docs/versioning) before choosing labels, routes,
`lastVersion`, or `includeCurrentVersion`.

## Search

Search is not automatically available merely because a site uses Docusaurus.
Choose and operate a search integration explicitly:

- Use [Algolia DocSearch](https://docusaurus.io/docs/search) when the site and
  eligibility fit its hosted crawler model.
- For private or offline sites, choose a maintained local-search plugin only
  after checking Docusaurus compatibility, index size, accessibility, and
  security.
- Scope crawlers to canonical production URLs and exclude previews, duplicate
  versions, and private content.
- Test indexing after deployment. A visible search box does not prove that the
  current site was indexed.
- Never place an Algolia admin key or write-capable credential in client
  configuration. Only the intended public search key may reach the browser.

## Build and Deployment Contract

The production build is the release gate. CI should:

1. Install from the committed lockfile without updating dependency resolution.
2. Type-check TypeScript configuration and custom React components.
3. Build the complete production site with broken internal links treated as
   errors.
4. Test the configured `baseUrl`, representative routes, redirects, and static
   assets against the generated output.
5. Scan dependencies and generated artifacts for secrets and unexpected files.
6. Run accessibility and performance checks on representative pages when the
   site is user-facing.

Deploy the generated `build/` directory as immutable static content. Keep build
and deploy identities separate where practical. A preview deployment must not
receive production credentials or publish into the production search index.

For GitHub Pages and other subpath hosting, verify the official [deployment
configuration](https://docusaurus.io/docs/deployment), especially `url`,
`baseUrl`, and `trailingSlash`.

## Review Checklist

- Docusaurus and Node.js compatibility was verified from current official
  documentation.
- All `@docusaurus/*` packages use one compatible pinned version.
- The lockfile is committed and CI performs a frozen install.
- MDX comes only from trusted, reviewed sources.
- Build plugins and remote content operate with least privilege and bounded
  egress.
- `url`, `baseUrl`, and `trailingSlash` match the production host.
- The production build fails on broken internal links.
- Search has an explicit provider, crawler or index lifecycle, and test.
- Version snapshots correspond to supported releases and have owners.
- Representative routes, assets, redirects, accessibility, and performance are
  verified before deployment.
